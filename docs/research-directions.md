# 跨生态近距离传输：可研究的方向与突破口

> 面向「本科阶段做出可发表、且能支撑港校 PhD 申请」的选题分析。
> 结论：**不要做「又一个传文件 App」，要做「为什么跨生态传不了」的测量与机制**。

---

## 一、问题被切成三段，断点各不相同

| 环节 | Apple 侧 | Windows/Android 侧 | 是否互通 |
| --- | --- | --- | --- |
| **发现**（谁在附近） | AWDL beacon + Bonjour | BLE 广播 + Wi-Fi Direct 发现 | ❌ |
| **链路**（怎么连） | AWDL（私有，需固件跳频） | Wi-Fi Direct / 软 AP | ❌ |
| **信任**（凭什么信） | Apple ID + 联系人证书 | Google 账号 / 二维码 | ❌ |

三段全断，但**难度差三个数量级**：

- 链路层最难（要固件支持、要驱动、要时序），前人已经撞过墙（AirDrop Anywhere 自述 dead end）；
- 发现层居中（只需被动接收，不需要精确时序）；
- 信任层最软（纯协议设计，可自由发挥）。

**研究价值不在「把三段都补上」，而在「证明某一段其实可以不补」。**

## 二、真正的空白（按可发表性排序）

### 空白 1：没有任何跨生态的近距离传输测量数据

现状：AWDL 有 OWL 的协议逆向论文（MobiCom/NDSS 系），Wi-Fi Direct 有零散的吞吐报告，但**没有人系统测量过「同一物理距离下，AWDL / Wi-Fi Direct / BLE / 软 AP 四种链路的发现延迟、能耗、吞吐、干扰」**。

这是一个典型的 measurement gap：不需要发明新协议，只需要严谨的实验设计与数据。可投 IMC / CoNEXT / MobiCom workshop，也容易做成数据集被引用。

> **2026-11-02 实测补充（重要）**：在校园网做跨子网实验（Mac 有线 `10.202.4.x` → Windows WiFi `10.233.x.x`）时，
> TCP 可通（~60 Mbps），但**两条发现通道全部失效**——UDP 广播与 mDNS 都是链路本地协议，跨子网根本出不去。
> 这修正了 RQ1 的前提：**在跨子网场景，发现不是「慢」，而是「不存在」**。
> 因此「发现延迟」只在同广播域内有意义；跨子网需要会合（rendezvous）机制，那是另一个问题，也是 beam relay 模式存在的原因。

**关键测量问题**：
- 发现延迟分布：从「打开分享面板」到「看到对方」的 P50/P95，四种链路各是多少？
- 能耗：发现阶段是常驻监听还是周期广播？手机侧掉电差异有多大？
- 干扰：AWDL 的社交信道（6/44/149）与常见 AP 信道的重叠情况，及其对吞吐的影响。
- 失败模式：为什么「看得到却连不上」？统计各链路的失败率与原因。

### 空白 2：「发现」与「数据面」可以解耦——但没人验证过

这是我目前看到**最有新意的点**。

AWDL 难，难在数据面：要在保持 AP 关联的同时，周期性跳到社交信道收发数据帧（availability window）。这需要固件级的多信道分时，消费级网卡做不到。

但**发现不需要数据面**：

- AWDL 设备会周期性在社交信道上发 beacon 与 action frame；
- 这些帧是**广播、冗余、容忍丢失**的，不需要精确时序，也不需要注入；
- 因此，一块**只收不发、固定停在社交信道**的网卡就能「看见」附近的 Apple 设备。

也就是说：**「能否发现」和「能否传数据」是两个独立问题，而前者对硬件的要求低一个数量级。**

如果这个假设成立，跨生态互通的路径就变成：

```
Windows 用第二块网卡在社交信道被动监听 → 看到附近的 iPhone/Mac（发现打通）
                                          ↓
                    用 Wi-Fi Direct 软 AP / 局域网建立数据通道（链路绕开 AWDL）
                                          ↓
                        传输走普通 TCP，不碰 AWDL 的数据面
```

**这可以写成一篇系统论文的核心论点**：*Discovery–Data Decoupling for Cross-Ecosystem Proximity Transfer*。

风险：需要验证「只监听能否稳定拿到 beacon」以及「收到 beacon 后能否解析出足够的身份信息」，且依赖第二块网卡（USB Wi-Fi，成本几十元）。

### 空白 3：链路能力的自动协商　（已有原型，见 `beam/internal/link`）

一旦承认「链路是异构的」（AWDL / Wi-Fi Direct / 软 AP / BLE / 网线 / 中转），就出现一个系统问题：**两端如何在 1 秒内协商出可用的链路组合？**

现有方案都是硬编码的（Android 优先 Wi-Fi Direct，Apple 只会 AWDL，LocalSend 只会局域网）。没有人做过「能力交换 + 候选链路排序 + 失败回退」的统一抽象。

**2026-11-02 进展**：已在 beam 里落地原型（`internal/link` + `proto.Caps`）：

- 候选链路按成本排序、逐条尝试、握手并入验证、协商记录可导出 JSON；
- **能力交换已实现**：握手后双方各发一次 caps（名字 / 端口 / 地址 / 支持的链路类型），对端声明的地址再做真实拨号验证。能力声明挂在现有 `Plan` 消息里、用空清单表示 hello，因此向前兼容、不新增帧类型。
- 实测暴露并修复的问题：假连接（TCP 通但握手失败）、候选污染（13 条里 12 条不可能通）、hello 之后连接被误关。三者都写成了回归测试。

**仍缺的一步**：拿到对端声明的地址后，**自动切换到更优链路**。当前只做可达性探测与提示，切换需要接收端同时在直连端口上监听（relay 模式下目前不监听），这是下一步的改造点。

这接近 ICE（WebRTC 的连通性检查）在近距离场景的移植，但多了一个维度：**链路本身要现造**（起热点、建 P2P 组）。

## 三、不建议做的方向（看着新，实际不是研究）

| 方向 | 为什么不建议 |
| --- | --- |
| 再做一版 LocalSend | 工程复刻，无新意，且已有成熟实现 |
| 完整移植 AWDL 到 Windows | 是工程不是研究；前人失败过；硬件挑食；且没有可推广的结论 |
| 「用 AI 优化传输」 | 没有真实问题支撑，属于套壳 |
| 纯协议设计（自定义加密/分块） | 已被 QUIC/TLS 充分解决，边际贡献低 |

## 四、建议的研究路线（6 个月，可切成三篇产出）

### 阶段一（1–2 个月）：测量，先出数据

- 搭实验床：Mac + Windows + Android，四种链路（AWDL / Wi-Fi Direct / 软 AP / BLE）；
- 用 beam 作为可控的传输实现（它已经能跑在任意 IP 链路上，且内置了时延/欠载/速率指标）；
- 产出：**发现延迟、吞吐、能耗、失败率**四张表 + 一份可复现的实验脚本。

**这一步的价值**：即使后面的假设被推翻，测量数据本身就能成文。

### 阶段二（2–3 个月）：验证「发现/数据解耦」

- 买一块支持 monitor 接收的 USB 网卡（AR9271/AR9271 系，几十元）；
- 写一个只监听社交信道的抓帧程序，统计能收到多少 AWDL beacon、解析出哪些字段；
- **判定标准**：能否在 5 秒内稳定识别到「附近有一台开启了 AirDrop 的 Apple 设备」。

**这一步是全篇的关键实验**。成功了，第二阶段就是一篇系统论文；失败了，退回阶段一的测量论文。

### 阶段三（2–3 个月）：系统化

- 把 beam 重构成「链路协商层 + 可插拔传输」；
- 实现能力交换、候选排序、失败回退；
- 评估：跨 Mac/Windows/Android 的成功率、端到端时延、用户操作步数。

## 五、实验协议（用 beam bench 采集）

工具已就绪：`beam bench`（见 `beam/README.md`「基准测试」一节），把一次传输拆成发现 / 建链 / 传输三段计时并追加 CSV。

### 自变量

| 维度 | 取值 |
| --- | --- |
| 链路 | 同一 WiFi 5GHz / 同一 WiFi 2.4GHz / Mac 热点 / 网线直连 / 经中转 |
| 数据量 | 10 MB（小块控制开销占比高）/ 100 MB / 1 GB |
| 发现方式 | `--peer`（自动发现）vs `--to`（已知地址，对照组） |

### 因变量

- 发现延迟（P50 / P95，分辨率 100 ms）
- 建链耗时（TCP connect + 加密握手）
- 吞吐（MB/s）、传输耗时
- 失败率与失败原因（CSV 的 `error` 列）
- 补充：两端 CPU 占用、设备电量（若测能耗）

### 控制变量

1. **同一物理距离**（1 米内，避免人体遮挡），同一房间；
2. **固定文件**，大小与内容一致（工具会缓存复用同一份测试文件）；
3. **关闭其他流量**（后台更新、同步盘）；
4. **每条件 ≥5 次**，取 P50/P95，不取平均（分布长尾明显）；
5. **交替顺序**（A/B/A/B），避免缓存与热效应对某一条件系统性地有利；
6. 记录环境元数据：设备型号、Wi-Fi 信道、RSSI、是否插电。

### 建议的第一轮（约两小时）

```
# 接收端固定一台，发送端换链路
beam recv --listen :9001 --out ~/Downloads --yes

beam bench --to <有线IP>:9001   --size 100 --runs 5 --label cable
beam bench --peer <设备名>       --size 100 --runs 5 --label wifi5g
beam bench --peer <设备名>       --size 100 --runs 5 --label hotspot
beam bench --to 127.0.0.1:9001  --size 100 --runs 5 --label loopback   # 基线：排除网络影响
```

`loopback` 那一组是**基线**：它代表「软件开销」的上限。任何真实链路的数字如果接近基线，说明瓶颈在网络之外；如果远低于基线，差值就是链路成本。

## 六、和现有工程（beam）的关系

beam 现在的定位是「能用的工具」，不是「研究成果」。要变成研究，需要三处改造：

1. **把链路抽象出来**：现在链路是「用户自己选 `--relay` / `--to` / `--peer`」，改成「声明能力 → 自动协商」；
2. **加测量钩子**：把发现延迟、建链耗时、吞吐、重传率写成结构化日志（已有部分指标，但不成体系）；
3. **可复现**：实验脚本 + 数据集，让别人能重跑。

## 七、对 PhD 申请的意义

- 一篇 workshop/short paper（IMC、CoNEXT、MobiCom workshop 都可尝试）+ 一份公开数据集，比「又一个大作业」有说服力得多；
- 港校 CS 申请看重「研究潜力」而非「工程量大」，**一个清晰的 RQ + 严谨的测量** 比「功能完整的产品」更对路；
- 失败也可写：**「我们发现跨生态传输的瓶颈不在协议而在发现层」** 本身就是有价值的负结果。
