## 二、三个关键发现

### 发现 1：跨子网时「发现」不是变慢，而是不存在

UDP 广播与 mDNS 都是链路本地协议。`10.202.4.x` 与 `10.233.x.x` 之间两条通道全部失效，只能靠手动指定地址。

**推论**：文献里讨论的「发现延迟」只在同一广播域内有意义。跨子网需要的是**会合（rendezvous）**，这是另一个问题——也正是中继模式存在的理由。

### 发现 2：NAT 造成单向可达

实测拓扑：

```
Mac 192.168.137.63 ──NAT──▶ 10.233.156.140 Windows
```

- Mac → Windows：通（3.6 MB/s）
- Windows → Mac：超时（不是拒绝，说明包被丢在 NAT 外）
- Mac 侧防火墙已确认关闭，排除本机因素

**推论（待验证）**：在这组条件下观察到一次方向差异；其原因尚未定位，不能直接推广为「可达性一定方向相关」。若后续受控实验确认该现象，则「谁发起连接」会成为一个需要显式考虑的设计变量——这一点目前只是假设。

### 发现 3：自建软 AP 不是免费的

该组（热点客户端 → 热点宿主）中位吞吐约为跨子网组的一半（3.6 vs 7.2 MiB/s），波动范围更大（2.5–4.8 vs 7.1–7.9）。每组仅 3 次、单日、单设备对，**不足以断言「热点一定更慢」**。

具体原因（频段、半双工、是否经转发）均未单独测量，不做归因；实际转发路径本轮也没有证据。

**推论**：软 AP 这条路在本组条件下没有表现出优势，但它是否普遍更慢、慢在哪里，需要分别测量。

## 三、阶段二：验证「发现与数据面解耦」

### 假设

AWDL 的数据面需要固件级信道调度（难），但**发现只需被动接收广播帧**（易）。若成立，一块只收不发的网卡即可「看见」附近的 Apple 设备。

### 判定标准

5 秒内稳定识别到「附近有一台开启了 AirDrop 的 Apple 设备」。

### 前置条件（已实测）

| 条件 | 现状 | 卡点 |
| --- | --- | --- |
| `awdl0` 接口存在 | ✅ 存在且 `active` | — |
| 能抓 `awdl0` 的帧 | ❌ `permission denied` | `/dev/bpf0` 属 root（`crw-------`），需 sudo |
| 第二台 Apple 设备（iPhone/iPad，开 AirDrop） | ❓ 未知 | 需要用户提供 |
| 目标设备不在飞行模式、屏幕解锁 | ❓ | 同上 |

**结论：阶段二当前被两件事阻塞**——抓包需要 root 权限，以及需要一台开启了 AirDrop 的 Apple 设备作为被观测目标。

### 实测：macOS 侧抓包（2026-11-02 18:34）

```
抓包前  awdl0  Ipkts 112  Opkts 103
抓 20 个包 / 30s → /tmp/awdl.pcap
抓包后  awdl0  Ipkts 112  Opkts 103     ← 计数完全没动
文件大小 24 字节（只有 pcap 全局头，0 个包）
```

**第二次实测（打开 Finder 隔空投送面板后，2026-11-02 18:40）：抓到 20 个包，计数器 220→262（收）/170→213（发）。**

```
fe80::78c3:81ff:fec2:9843   ← 本机 awdl0（链路本地地址由 MAC 7a:c3:81:c2:98:43 推导）
fe80::6cd5:29ff:febb:44d2   ← 另一台 Apple 设备，10 个包，端口 49248
服务类型：_companion-link._tcp（Continuity/接力）
TXT 记录：rpBA=62:59:AF:71:E1:81（对端蓝牙地址）、rpAD=9d118a124c3c
```

**这是正结果，但它证明的事情和我们原先设想的不一样。**

第一次（2026-11-02 18:34）是负结果（0 包、计数器不动），两种可能尚未区分：

1. macOS 不向用户态暴露 `awdl0` 的帧（封装在内核/driver 里）；
2. 当时确实没有 AWDL 流量——macOS 的 AWDL 是按需激活的，只有打开「隔空投送」面板或共享菜单才会真正收发。

**区分方法**：先打开 Finder 的「隔空投送」窗口（保持打开），再跑一次同样的抓包。若计数器开始增长但仍抓不到包 → 是第 1 种（接口屏蔽）；若计数器仍不动 → 是第 2 种（没有流量，需要检查 iPhone 的 AirDrop 是否真在广播）。

### 修正后的结论：AWDL 的价值是「链路」，不是「发现」

抓到的是 **IPv6/mDNS 流量**，也就是运行在 AWDL **数据面**之上的 IP 报文。它之所以能看到，是因为**这台 Mac 本身就是 AWDL 的参与者**——系统把它接入了 AWDL 的调度，才有数据帧送到 `awdl0`。

这直接推翻了原假设中的关键一步：

> 原假设：发现只需被动接收广播帧，所以一块只收不发的网卡就能看见附近的 Apple 设备。

**实际不成立。** 原因有两条：

1. **发现本身就是数据面流量**。AirDrop/接力的发现是 mDNS（IPv6 组播），跑在 AWDL 的数据通道里，不是裸的 beacon。要收到它，就必须处在 AWDL 的可用窗口（availability window）调度中；
2. **被动监听只能碰运气**。AWDL 设备在社交信道与业务信道之间跳频，固定停在一个信道上的监听者只能截获调度间隙里的少量帧，而且无法解码非广播部分。

所以准确的结论是：

| 原以为 | 实际 |
| --- | --- |
| 发现是廉价的，数据面是昂贵的 | 发现和数据面共用同一套链路调度，**一样昂贵** |
| 只收不发就能发现 | 必须成为 AWDL 参与者才能稳定看到发现流量 |
| AWDL 的价值在「发现协议」 | AWDL 的价值在**提供一条无需基础设施的链路**；发现只是跑在上面的普通 mDNS |

**这条修正对研究方向有实质影响**：既然发现离不开链路，「发现/数据面解耦」作为系统论点不成立，应放弃；而「跨生态测量」和「链路协商」两个方向不受影响，仍然成立。

### 解除阻塞的三条路

1. **授权 sudo 跑一次抓包**（最小验证：`sudo tcpdump -i awdl0 -c 20 -w awdl.pcap`，看能否抓到 beacon）；
2. **用第二台 Apple 设备**（iPhone 即可）作为目标，验证「能否识别」而不只是「能否抓包」；
3. **先做协议层的离线验证**：按 OWL 公开的帧格式实现 beacon 解析器，用抓到的 pcap 回放测试。不依赖硬件，可先做。

## 四、建议的下一步顺序

| 顺序 | 动作 | 依赖 | 产出 |
| --- | --- | --- | --- |
| 1 | `sudo tcpdump -i awdl0` 抓 20 个包 | root | 判断「能否抓到 AWDL 帧」——最关键的二分 |
| 2 | 若抓到 → 写解析器，识别 beacon 中的设备标识 | 第 1 步的 pcap | 阶段二核心证据 |
| 3 | 若抓不到 → 转做「链路协商层」系统实现 | 无 | 阶段三的系统贡献 |
| 4 | 补同网段对照组 | 切换网络（用户暂不愿） | 完成吞吐归因 |

第 1 步是整个研究的**关键二分点**：抓到，阶段二成立；抓不到，立刻转向阶段三，不浪费时间。
