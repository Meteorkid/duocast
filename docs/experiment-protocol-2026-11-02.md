# Mac–Windows 近距离传输实验方案与操作规程

> 版本：v1，2026-11-02；状态：拟定协议，正式实验前在第 6 周冻结。
> 对应：[研究计划](research-plan-2026-11-02.md)。下列机制、日志字段和分析能力属于待实施要求，现有 Beam 尚未全部具备。

## 1. 实验目的与顺序

先回答“现有两台机器能否离线建链”，再回答“候选机制是否比合理的简单流程更有效”。以用户发起到接收校验确认这一完整任务为观测单位。

顺序为 E0 能力探索 → 测量工具验收 → 小规模方法探索 → 冻结协议 → E1/E2 主实验 → E3 恢复消融 → E4 已连接参考 → 统计与解释。

文件传输方向与网络角色独立：即使两种方向都由 Windows 建 AP、Mac 加入，也属于有效的双向文件传输。若反向 AP 角色不可用，不将其伪造为第二条可选链路。

## 2. 设备与环境盘点

每个设备对一个 `device_pair_id`。初始只有 P01，一台 Mac 和一台 Windows；未来增加设备时使用新的 ID。

P01 的 Windows 已由用户提供：Xiaomi Redmi Book 16 2024（Gen12 CPU），Windows 11 家庭版中文版 64 位，10.0.26200 / Build 26200；Intel Wi-Fi 6 AX203，驱动 23.60.1.2（2024-05-01），状态 Up。该信息作为已知设备清单，原始盘点输出与实际 API 支持仍由 E0 留证。Mac 为 Apple Silicon，完整设备/系统信息待补。

先在现有驱动和系统上做 E0。若版本变更成为排障必要步骤，为新组合分配新的配置 ID，旧结果保留；不能把升级前后记录混成同一硬件条件。

| 信息 | 记录要求 |
| --- | --- |
| 设备 | 型号、CPU、内存、操作系统版本/build；公开材料用匿名设备 ID |
| 无线 | 网卡型号、驱动版本、Wi-Fi Direct/Legacy AP 实测状态、BLE central/peripheral 实测状态 |
| 权限 | 蓝牙、网络访问、沙盒/签名形态、防火墙相关状态；记录提示次数和是否完成 |
| 拓扑 | 主试验前无外部连接；实际 AP 所在设备、客户端、接口、地址、频段/信道 |
| 场地 | 同一房间，桌面固定位置、约 1 m、无遮挡；记录朝向与可取得的 RSSI |
| 运行状态 | 两端接电、同一电源模式、应用前台、同样后台负载控制策略 |
| 软件 | 原型版本、策略配置、协议/schema 版本、二进制 SHA-256；无 Git 时保存源码快照及文件清单哈希 |
| 存储与文件 | 磁盘/文件系统、剩余空间、预读策略、数据字节数和 SHA-256 |

### 2.1 第一天的只读信息采集

Mac 终端：

```bash
sw_vers
system_profiler SPHardwareDataType SPAirPortDataType SPBluetoothDataType
```

Windows PowerShell：

```powershell
Get-CimInstance Win32_OperatingSystem | Select-Object Caption, Version, BuildNumber
Get-CimInstance Win32_ComputerSystem | Select-Object Manufacturer, Model, TotalPhysicalMemory
Get-NetAdapter -Physical | Select-Object Name, InterfaceDescription, Status
netsh wlan show drivers
netsh wlan show wirelesscapabilities
```

这些输出用于盘点，不代表 API 路线已验证。共享实验包前删去序列号、个人设备名、无关 SSID 与其他网络标识；保留研究需要的型号、版本和匿名接口信息。若某命令不可用，保存错误并从系统信息界面补录，不据此判定硬件不支持。

### 2.2 “无基础设施”的验证

- 在两端确认没有连接外部 Wi-Fi、以太网、手机热点、VPN 或公网中转；无线电本身保持开启。
- 记录本次数据接口、对端地址及所创建 AP 的标识；协议中的外部中转路径关闭。
- 用实际接口与路由证据确认流量走临时网络。仅“打不开网站”或“ping 不通”不能证明实验隔离正确。
- 环境中自然存在的无线信号作为背景条件记录；没有专用设备时不声称控制了干扰强度。

## 3. 起始状态定义

| 状态 | 应用/权限 | 信任 | 数据网络 | 用途 |
| --- | --- | --- | --- | --- |
| I：首次安装授权 | 首次启动，权限可能未授予 | 无 | 无 | 记录一次性配置流程，不混入正式耗时 |
| U：首次会合冷启动 | 两端应用已就绪，必要系统权限已授予 | 无已存对端信任 | 无临时 AP、关联和共同 IP 网络 | E2；用户核验与接收确认计入时间 |
| P：已配对冷启动 | 两端应用已就绪，权限已授予 | 保留已验证的对端身份 | 无临时 AP、关联、TCP/控制连接；旧会话信息失效 | E1、E3；适用于重复使用场景 |
| W：已连接 | 两端应用已就绪 | 对端已确认 | 临时数据网络已建立、IP 可达；每次新建传输连接 | E4；观察传输部分成本 |

U/P 的“冷”指网络会话冷启动，不表示整机重启、磁盘冷缓存或每轮重新安装。开始前两端应用都已打开，不将常驻接收端的测试称为应用启动测试。

每轮 U/P 重置只针对研究应用及其创建的网络：关闭上一轮 AP/P2P 会话、断开连接、使上一轮发现结果和地址失效；U 额外清除本应用保存的对端信任。系统授权保留，不反复重置整个系统隐私数据库。

使用 `reset_passed` 和实际状态事件证明重置完成。若 OS 无法完全清掉底层扫描缓存，采用固定间隔并记录缓存不可控范围，所有方法同样处理。

## 4. 方法和对照

| ID | 方法 | 公平比较要求 |
| --- | --- | --- |
| B0 | 人工标准建链：启动已验证 AP 流程，另一端人工选择/加入，再用 Beam 传输 | 与自动方法同一无线角色、文件、传输代码、加密与校验；从第一步操作开始计时；允许正常系统凭据缓存，但按 U/P 规则一致设置 |
| B1 | 简单自动策略：相同控制通道、固定角色与阶段顺序；正确等待系统就绪事件；遇可恢复错误整体重试一次 | 不人为加长 sleep、禁用必要缓存或减少权限；与 M 同一全局截止时间和一次恢复预算 |
| M | 候选机制：记录并验证阶段状态，只保留仍有效的进展，选择必要恢复起点 | 与 B1 共用代码主体，差异集中在状态有效性与恢复决策；不得单独换更快数据面 |
| M0 | M-no-recovery：保留正常建链路径，关闭阶段恢复，故障后明确结束 | 只用于 E3 判断恢复模块的作用；不能作为唯一主基线 |
| W-ref | 已建临时网络上的同一 Beam 数据面 | 传输参考，不与冷启动方法作“谁总时间更快”的排名 |

B0 由同一操作者按固定步骤执行，正式记录前练习至流程熟悉；操作者不能预先给某方法建好网络。记录点击、选择、输入、核验和确认次数，等待不算操作。结果描述为该操作者的任务流程成本，不作为用户体验研究。

产品对照为可选补充：LocalSend/Feem 在同样起始条件下记录是否需人工组网、完成时间和步骤。产品不能自动组网时，包含其文档要求的人工步骤；不把“只打开 App”的失败当作其整个产品能力。NearDrop 只有支持实际设备对时才加入。跨产品结果用于应用参考，机制归因仍以 B1 与 M 为准。

## 5. E0：能力与可行性验证

### 5.1 分步流程

1. 保存设备、驱动、权限和初始网络状态。
2. 使用 Microsoft 官方 Legacy AP 路线，在 Windows 没有上游网络的状态下启动 AP，记录 API 结果、实际可见网络及生命周期。参考[官方样例](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/wifi-direct-legacy/)。
3. Mac 作为普通 Wi-Fi 客户端人工加入，确认关联、地址可用与 TCP 端口可达。成功标准不止是 AP 启动函数返回。
4. 用现有 Beam 发送一个 1 MiB 合成文件，核对接收 Result 与文件哈希；保持网络角色不变，反向再传一次。
5. 主动结束 AP，再重建，完整尝试 10 次，跨至少两个时段。一次流程可含两个方向，分别记结果。
6. 独立验证 BLE：一个端点广播/GATT 服务，另一个连接，双向交换带序号和随机会话标识的小消息；断开再连接，重复 10 次。实际 central/peripheral 角色由能力结果决定。
7. BLE 可交换消息后，再验证其与 AP 建立过程是否互相影响。BLE 控制消息成功不直接记为 Wi-Fi 建链成功。

若某必要能力不支持，记录 `capability_not_supported`、OS/API 错误和发生步骤；它属于适用性结果，不与支持设备上的传输超时混为一类。只检查实际可用的 Mac AP 反向路线，不默认“互联网共享”在当前无源接口条件下一定工作。

### 5.2 E0 现有 Beam 使用边界

人工网络已建立后可使用现有命令：

```text
接收端：beam recv --listen :9001 --out <实验专用接收目录>
发送端：beam send <合成测试文件> --to <本次实际对端地址>:9001
```

Windows 使用 `beam.exe`。地址来自本轮新建网络，不硬编码历史校园网地址。自动接受只在双方事先授权的研究会话中启用；U 状态需要的身份/接收确认必须保留。现有 `beam bench` 可测已建 IP 链路上的传输，不能单独作为 E1/E2 冷启动测量器。

## 6. 测量工具的最小改造与验收

主实验单文件，以现有逐文件 Result 为接收确认。优先补记录和截止时间，不要求先增加断点续传、多流或完整跨平台 UI。

| 项目 | 改造要求 | 验收 |
| --- | --- | --- |
| 试次关联 | `experiment_id/condition_id/trial_id/device_id`，两端共享 trial_id | 两端事件可一一对应；重复 ID、缺事件显式报错 |
| 阶段事件 | 会合、身份核验、AP 就绪、关联、地址可用、TCP、认证、传输开始、接收校验、Result 到达 | 事件标明发生端；不存在的阶段不补假时间 |
| 统一计时 | 发起端用同一单调时钟记录任务起点与确认终点 | 已有 Go `time.Now`→`time.Since` 保留；不直接相减两端墙钟 |
| 完成证据 | 接收端记录实际字节数、期望/实际 SHA-256、重命名结果；发起端记录 Result | 破坏测试数据、接收写入失败时不能报告 success；回执丢失标记不确定完成状态 |
| 阶段状态 | `not_run/success/timeout/error`；未执行时间为 null | 指定 IP 时发现为 not_run，不进入发现延迟统计 |
| 截止时间 | 握手、传输、确认和恢复均受剩余预算约束 | 模拟阶段阻塞后仍有明确终态；每次结束立即记录 |
| 单位 | `payload_bytes` 为唯一数据量基准 | 1,048,576 bytes/s = 1 MiB/s = 8.388608 Mbit/s |
| 分组 | 依据 condition_id，不仅按 label×size | 方向、状态、方法、版本不同的条件不能静默混合 |
| 分位数 | 分析明确采用一种约定，例如线性插值 type 7 | Go 与 Python 的固定输入核对一致；不足样本不输出误导性精度 |

验收采用可控的合成数据与本机/两机测试：正常文件、哈希不符、接收写入失败、指定 IP 跳过发现、阶段阻塞、回执未到、日志写入中断。只验证会影响实验结论的逻辑。

已知源码位置：`beam/cmd/beam/bench.go` 的发现/连接/握手/单位/逐批记录，`beam/internal/proto/proto.go` 的逐文件 Result，`beam/scripts/bench-summary.py` 的分组与分位数。历史 CSV 和代码版本先保留，不覆盖为新的正式记录。

## 7. 成功、耗时与失败定义

### 7.1 计时边界

`t0`：两端应用已按指定状态就绪，操作者在文件发送端的试验启动器点击“开始试次”，由该机立即记录单调时间。所有方法使用这一统一入口；B0 随后在相应电脑上执行启动 AP 的第一步，自动方法随后开始会合。操作者移动到另一台电脑及后续人工确认的时间都包含在内。

`t1`：发送端收到本文件成功 Result，且能够关联接收端的校验和重命名事件。

`T_task = t1 - t0`，两者取文件发送端同一单调时钟。即使 Mac 发送而 AP 操作发生在 Windows，也不把 Windows 操作时刻换算为 Mac 的起点。接收端本地的处理耗时在其自己的单调时钟上计算。墙钟仅用于日志对齐和人工核查，不用于跨机单向时延。

分阶段记录控制会合、用户核验、AP 建立、关联/地址、TCP、认证、传输确认、恢复。阶段可能重叠，记录区间和重试序号；分阶段总和不能自动替代端到端时间。

W-ref 的起点为已建链路上发起新传输，单独命名 `T_warm_transfer`，不与冷启动起点混用。

### 7.2 成功语义

- 文件字节数与预设一致，接收端 SHA-256 一致，文件关闭及重命名完成，发送端收到成功 Result，且在该条件的截止时间内。
- 这里衡量应用层保存完成，不衡量断电后的持久化；全部方法使用相同语义。
- 若接收端确认保存，而发送端未收到回执，记录 `receiver_completed=true` 与 `outcome=indeterminate`；协议任务未完成，不写成“文件一定丢失”。
- 两端连接成功但数据未通过校验，不能记作传输成功。

### 7.3 候选截止时间

| 数据量 | 完整任务截止时间 D |
| --- | --- |
| 1 MiB | 60 s |
| 100 MiB | 180 s |
| 1 GiB | 600 s |

这些是便于预实验执行的工作参数，不是性能目标或已验证能力。各阶段预算在 E0 后拟定，所有阶段均截断于剩余总预算。第 6 周根据任务需求和探索耗时统一冻结；同一状态/文件规模的所有方法使用同一 D，恢复计入 D，不能按方法单独放宽。

### 7.4 主要指标

1. **期限内完成率：** `success_before_D / all_valid_attempts`；同时列出分子和分母。
2. **完成率—时间曲线：** `F(t) = count(confirmed completion at or before t) / all_valid_attempts`。失败试次留在分母。
3. **任务成本：** 成功样本的中位数和 IQR；另报告含全部试次的截止时间惩罚分数 `L_D=T_task`（成功）或 `D`（未成功）。`L_D` 是约定的任务损失，不是实际运行耗时。
4. **人工操作数与核验等待：** 明确计数规则；I、U、P 分开。
5. **诊断指标：** 各阶段成功率、实际耗时、恢复次数和原因、确认后的有效吞吐。吞吐按实际字节数计算，不用吞吐解释全部任务体验。

## 8. 正式实验矩阵

### E1：已配对冷启动主比较，360 次

固定 P 状态、约 1 m、同场地；方法 B0/B1/M，方向 Mac→Windows 与 Windows→Mac，文件 1 MiB/100 MiB/1 GiB，每格 20 次。总计 `3×2×3×20=360`。

每个配对区组固定方向、文件与起始状态，包含全部三个方法；方法顺序随机或平衡轮换。每个条件分散到 10 个实验日期，每日 2 次，约每日 36 次 E1 任务。每次重新建立网络，不能在一个 AP 会话内连续传 20 次冒充冷启动。

### E2：首次会合，60 次

U 状态，B0/B1/M，两个文件方向，100 MiB，每格 10 次，总计 `3×2×1×10=60`。分散于至少 5 个实验日期，每日每格 2 次。每轮重置本应用的对端信任，保留系统权限；人工核验时间纳入任务时间。

E2 分析首次连接的成本与功能，不根据 10 次成功就宣称普遍高可靠。若方法依赖 OS 保存凭据，必须说明 U 条件如何处理，并对所有方法保持一致。

### E3：阶段恢复与消融，60 次

P 状态，100 MiB，预先固定一个方向（建议 Mac→Windows；第 6 周冻结），方法 B1/M/M0，两类连接前故障，每格 10 次，总计 `3×2×1×1×10=60`。

默认故障候选：

- F1：能力/身份信息已交换，数据连接尚未完成时，控制通道断开一次。优先用研究进程的会话级断开触发，记录实际发生阶段与影响。
- F2：第一次 AP 启动请求返回一次可恢复错误，随后恢复正常；采用明确标记的软件故障注入，不称为硬件真实故障率。

两类故障在 G2 根据真实可复现失败和可触发性确认；正式采集前冻结事件位置、持续条件和重试预算。注入命令没有触发实际目标状态时记为 `injection_not_delivered`，保留记录并按预定规则补试，不记作算法失败。

每个区组包含同一故障下三种方法；跨至少 5 个日期。与自然运行的 E1 分开统计。中途传输断线、断点续传和系统睡眠不在核心矩阵；如另测，作为单独探索集。

### E4：已连接传输参考，30 次

W 状态，同一 Beam 数据面，两个方向，三个文件规模，每格 5 次，总计 `1×2×3×5=30`。保留与主实验相同的加密、校验及文件策略。用来观察传输部分，不估计稳定尾延迟。

### 探索与缩减规则

E0 及第 5 周每关键条件约 3–5 次的调试数据全部标记 `phase=exploratory`。E1–E4 标记 `phase=confirmatory`，不得混合增大样本量。

正式候选总数 510 次。若工时不允许，先缩减大文件或产品扩展，保留强基线、两个方向、冷启动及恢复实验；在第 6 周锁定修订版和总次数，再开始正式采集。不得跑到出现显著结果才停止。

## 9. 每一试次的操作规程

1. 读取预先生成的试次清单，确定 ID、方法、方向、状态、文件、故障与截止时间。
2. 核对软件哈希和配置，启动两端日志；接收输出指向该试次的专用目录。
3. 执行 U/P/W 对应重置，保存 `reset_passed` 证据；未满足起始条件不启动正式计时。
4. 按统一策略预读合成文件一次，生成和预读均在 t0 前完成。记录缓存策略，不能保证或声称每次完全命中内存缓存。
5. 操作者触发任务，记录 t0；按本方法的固定步骤操作。期间不临时帮某个方法改地址、切频段或延长预算。
6. 保存最终 Result/错误/超时，记录 t1 或失败终点、人工操作数、字节数、哈希及实际接口。
7. 结束本轮，保存两端日志和摘要；检查 trial_id 和关键事件是否匹配。自动检查只标记异常，不删除不利结果。
8. 在预先规定的轮间间隔后进入下一试次；将环境变化记入日志。清理仅限已验证的合成接收文件，原始日志与摘要保留。

同一实验日期使用同样场地/摆位、应用状态和电源模式；方法顺序不能总是 B0→B1→M。错误导致轮次延长是结果的一部分，不因“不好看”重新启动计时。

## 10. 文件与环境控制

- 尺寸用整数：1 MiB=1,048,576 bytes；100 MiB=104,857,600 bytes；1 GiB=1,073,741,824 bytes。
- 使用预生成、内容固定的伪随机合成文件，记录生成方式、seed 和 SHA-256；各方法传相同文件，不用真实私人文件。
- 主实验关闭应用级压缩和额外并发；若数据面本来没有这些功能，保持现状。
- 各方法采用相同文件预读策略；源文件生成不计入任务时间。接收端独立目录避免旧文件影响命名与覆盖行为。
- 固定约 1 m 和无遮挡。5 m/遮挡只作为另行预定的扩展条件，未测时不作距离稳健性结论。
- 频段、信道、RSSI 取实际可读取值；无法读取填 unknown，不根据速度猜测。
- 需要比较功耗时先明确仪器与方法；主计划不把电池百分比变化当精确能耗证据。

## 11. 记录格式与文件组织

建议的实验包结构（本轮仅定义，不创建假数据）：

```text
experiments/<experiment_id>/
  protocol.md                # 本次冻结协议
  manifest.json              # 设备、版本、环境、方法配置
  trial-order.json           # 随机种子与完整计划顺序
  raw/<trial_id>/sender.jsonl
  raw/<trial_id>/receiver.jsonl
  raw/<trial_id>/operator.json
  summaries/trials.jsonl      # 一试次一条，不覆盖原始记录
  analysis/                  # 数据检查、图表脚本和派生输出
  checksums.sha256
```

`condition_id` 至少编码设备对、方法、方向、拓扑、起始状态、payload_bytes、故障条件和软件配置版本。阶段日志至少包含以下字段：

| 字段组 | 必需内容 |
| --- | --- |
| 身份 | experiment_id、phase、condition_id、trial_id、block_id、session_id、date、device_id |
| 条件 | method、direction、start_state、payload_bytes、fixture_sha256、software_hash、config_hash |
| 事件 | event_name、event_owner、attempt_index、elapsed_ns、wall_time、stage_status |
| 网络 | control_medium、ap_role、selected_interface、candidate_id、path_state、band/channel/RSSI 或 unknown |
| 结果 | outcome、failure_stage、error_code、receiver_completed、result_received、bytes_received、hash_match |
| 预算 | deadline_ms、recovery_limit、timeout_stage；未执行阶段耗时为 null |
| 操作 | manual_actions、manual_wait_ms、reset_passed、injection_delivered、operator_deviation |

不在日志中写热点明文密码、会话密钥或可复用配对秘密。地址若需公开，提供保持拓扑关系的匿名映射；本地原始记录保留实际接口信息以核对路径。

历史 `campus.csv/loopback.csv` 原样保留并标记 legacy/exploratory；若做单位转换，生成带来源和转换规则的派生文件，不能把 `0` 直接改成“发现成功”。

## 12. 失败、缺失与剔除规则

有效试次的终态：`success/timeout/error/indeterminate`，全部计入完成率分母。阶段未执行用 `not_run`。能力不支持在 E0 单列适用性，不静默隐藏。

技术无效试次仅限预先定义的情形：起始状态不符、软件/文件版本错误、日志损坏导致主终点无法判定、操作者误执行非该方法步骤、预定故障未实际注入。保留原记录、无效原因和补试关联 ID。若日志缺失本身由系统崩溃导致，记录为系统失败，不能借“日志坏了”排除。

正式试次中的真实连接失败、权限意外失效、磁盘错误、校验错误或超时不因罕见而删除。故障类型按观察记录；尚无证据的根因填 unknown，不把“连接慢”自动归因为校园网限速或无线干扰。

中途发现实现错误时暂停该配置的正式采集，保留已有版本数据，修复后用新软件哈希和协议修订号重启受影响条件。不同版本不混在一个主结果里。

## 13. 分析计划

1. 先核对计划次数、实际次数、有效/无效/补试数量、阶段状态和接收证据；无输出的计划任务也列为未执行，不能消失。
2. 每个条件报告成功数/总数、失败类型、完成率曲线、成功耗时中位数/IQR、人工操作数。阶段耗时按该阶段实际执行且成功的试次统计，同时给阶段成功率，避免只挑最终成功任务。
3. 主比较 M 对 B1，B0 提供任务操作参考。按相同区组计算完成率差和 `L_D` 差值，保留配对；成功任务耗时差仅作条件性补充。
4. 汇总各日期的配对效应并展示分布；如给 95% 区间，按日期重采样，并在日期内重采样完整配对区组，保留组内所有方法。注明日期数、随机种子和 10,000 次重采样；小日期数时区间为探索性，不声称普适保证。
5. 成功比例以成功数/总数、各日期结果和上述按日期/区组重采样的区间展示；不默认同一天的重复试次相互独立，也不把它们当作跨设备样本。
6. E1 的每格 20 次足以开始比较分布与机制趋势，不足以稳定估计 P95。P95 仅作探索展示；若尾部成为核心主张，预先选定关键条件另做约 100 次以上及区间分析，而非从现有最有利条件事后挑选。
7. 主要报告效应量和不确定性，不围绕单个 p 值作结论。若增加假设检验，事先确定主比较与多重比较处理，避免按结果挑检验方法。
8. 两个方向分开报告；三个规模分面。不能把 1 GiB 的吞吐与 1 MiB 的总延迟混成单一优胜率。
9. 恢复实验说明注入位置和机制响应；不将注入失败比例解读为现实发生概率。自然故障单独报告。
10. E1 调参数据禁止进入正式分析。若正式结果促使更改方法，变更后的结论由新一轮确认数据支持。

## 14. 图表与结论检查

| 输出 | 回答问题 | 必须同时呈现 |
| --- | --- | --- |
| 能力与路径表 | 这对设备有哪些真实可用流程 | 支持/不支持/未测、系统版本、证据 |
| 完成率—时间曲线 | 在给定时间内谁更可能完成 | 全部有效试次分母、文件规模与 U/P 状态 |
| 阶段时间图 | 成本发生在哪一步 | 人工与自动耗时、失败阶段样本数、重叠阶段说明 |
| M−B1 区组差值 | 方法差异是否稳定 | 各日期结果、效应区间、同样起始条件 |
| 恢复消融图 | 收益是否来自阶段恢复 | B1/M/M0、相同故障和预算、额外恢复开销 |

结论不得超过证据：仅一对设备不推导跨所有网卡兼容；仅合成故障不推导现实故障率；仅与人工流程比较不证明算法创新；API 调通或修正基础错误不自动构成研究贡献。若强基线已足够，应在论文中据结果简化机制。

## 15. 正式采集前冻结清单

- [ ] E0 已验证真实无线链路，控制通道方案与人工边界明确。

- [ ] 单文件成功终点、字节单位、单调计时与阶段状态通过验收。
- [ ] I/U/P/W 状态可区分，重置步骤与缓存策略已固定。
- [ ] 主要 RQ、方法版本、条件矩阵、次数、截止时间和故障位置已锁定。
- [ ] 随机顺序和种子已生成；探索集与正式集分离。
- [ ] 日志、无效试次规则、补试规则和分析口径已冻结。
- [ ] 根据探索结果完成样本/工时核定；没有按正式结果删减条件。
- [ ] 相关工作比对已明确具体机制差异；论文贡献不依赖未经核实的“首次”。
