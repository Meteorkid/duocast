## 2. G1a：数据链路的已有证据

### 2.1 已经验证的（可复现）

| 事实 | 证据 | 强度 |
| --- | --- | --- |
| beam 能在已有 IP 链路上完成传输、SHA-256 校验与接收确认 | 多次单文件/多文件传输；1 GiB 单次 144 s | 强 |
| Mac → Windows 跨子网直连可用 | `campus.csv` 7 条 + 后续多次 | 强 |
| 中转配对 + 升级到直连可用 | `paired-upgrade.md`，5/5 成功 | 中（样本少） |
| 反向连接超时 | 单次测试 | 弱 |

### 2.2 没有验证的（关键缺口）

| 缺口 | 说明 |
| --- | --- |
| **无上游 AP 建链** | 此前 `192.168.137.x` 那段，Windows 热点以上游校园 Wi-Fi 为源，**不是「无基础设施」** |
| **Legacy AP（Wi-Fi Direct 软 AP）** | 从未在 AX203 上尝试；型号与「网卡 Up」不构成支持证据 |
| **跨两时段 10 次流程** | 未做；现有数据集中在同一天两小时内 |
| **角色反转** | Mac 提供 AP 的路径未验证（也不在首选路径内） |

### 2.3 一条会误导判断的事实

Windows「移动热点」**要求先有可共享的上游连接**（微软文档与本次实测一致：无外网时开关打不开）。

这带来两个后果：

1. **那次记录里，热点宿主仍然连着校园网**，所以它只能说明「有上游时链路能通」，**不能证明无基础设施条件**。判断某次记录是否算「无基础设施」，要看当时的**实际起始连接与流量路径**，而不是看功能叫什么、是不是 ICS；
2. 真正对应计划的是 **Legacy AP（`WiFiDirectAdvertisementPublisher` + `WiFiDirectLegacySettings`）**，该路径没有上游概念，但必须实测是否可用。

### 2.4 2026-11-03 首次实跑：加入 + 双向传输（有上游）

这是目前唯一一次真正跑通的「Mac 接入 Windows 自建 AP 并双向传输」。

| 观察 | 结果 |
| --- | --- |
| Windows AP | Mobile Hotspot，SSID `beam-e0`，网关 `192.168.137.1` |
| AP 地址 | Wi-Fi Direct 虚拟适配器 `192.168.137.5`（接收端在此地址可达） |
| Mac 加入 | 成功，地址 `192.168.137.63` |
| 正向 Mac → Windows | 1 MiB，4.0 MB/s，验证码 `Z3VY-XQX6`，接收端回 Result |
| 反向 Windows → Mac | 7.0 MB（`beam.exe`），验证码 `YPTP-TDSM`，落盘 SHA-256 与源一致 |
| TCP | `.5:9001` 可达；`.1:9001` 不可达（ICS 网关接口被防火墙挡住） |

**关键限制：这次不是「无基础设施」。** Mobile Hotspot 是 ICS 转发，它要求宿主有可共享的上游连接（实测：断开 STA 后拿不到 connection profile，热点起不来）。因此本次只能证明：

- Mac 能作为普通 Wi-Fi 客户端加入 Windows 自建的 Wi-Fi；
- 加入后 TCP 可达、双向文件传输与校验成立。

它**不能**证明 G1a 的「无上游」条件。G1a 仍需一个宿主没有任何上游连接的 AP。

**另一个未解决的问题**：Legacy AP（Wi-Fi Direct，唯一不依赖上游的路径）在本轮尝试中**没有被 Mac 扫描到**（`networksetup` 报 `Could not find network beam-e0`，两次）。是广播未发出、还是 macOS 对 P2P SSID 的可见性限制，尚未区分——需要手机扫描做对照。

## 3. G1b：控制通道的已有证据

### 3.1 macOS 侧（本机一次记录，非普遍结论）

在**这一台机器、这一版系统**上观察到：

| 观察 | 现象 |
| --- | --- |
| 裸命令行二进制调用 CoreBluetooth | 进程 `SIGABRT`，无输出 |
| 包成 `.app` + `NSBluetoothAlwaysUsageDescription` | `adapter.Enable()` 阻塞，等待授权提示 |
| 从终端执行 bundle 内二进制 | 未能取得权限 |

**只能说**：在这台机器上，命令行进程未能直接获得 BLE 访问能力，打包为 app 并完成授权是可行的下一步方向。

**不能说**：不能据此断言「macOS 一律如此」「所有版本都要求 app bundle」——本记录没有覆盖其他系统版本、其他机型、其他签名形态（如带开发者 ID 签名的命令行工具）。这些都需要单独验证。

### 3.2 Windows 侧与跨系统

- 未做任何 BLE 实测。
- 跨系统双向小消息交换：**未做**。
- BLE 与 AP 共存（同一网卡并发 BLE + 软 AP）：**未测**，不能假设支持。

### 3.3 一条必须写进方法的限制

「扫描到设备名」「RSSI 很近」「适配器 Up」都**不能**作为可用性证据。可用性只能由「实际建立 GATT 连接并交换带序号的消息」证明。

## 4. AP 共存的假设与风险

**先分清两个适配器**：蓝牙适配器与 Wi-Fi 适配器是独立的设备节点，型号、驱动、供电都不同。AX203 是 Wi-Fi 侧型号，**不能**用它推断蓝牙侧能力；反之亦然。

**也不能假设两者共用同一个射频**：即使 BLE 与 Wi-Fi 在同一颗组合芯片上，并发行为仍取决于驱动与固件，属待测项。

| 假设 | 风险 | 如何验证 |
| --- | --- | --- |
| 蓝牙适配器与 Wi-Fi 适配器可同时工作 | 可能是同一组合芯片，AP 模式下 BLE 受限或丢包 | 分时测量：只开 BLE → 只开 AP → 两者同开，比较 BLE 消息延迟与 AP 吞吐 |
| AP 建立期间 BLE 消息不中断 | 信道切换导致 BLE 丢包 | AP 启动前后各发 10 条消息，统计丢失与延迟 |
| AP 与 STA 共存（同时连上游 AP） | 多数网卡支持但会降速 | 不属本实验主场景（无上游），仅记录 |

这些都需要真机，属于**两机实操待办**（见第 6 节）。

## 5. Windows 只读采集清单（不改任何配置）

在 **PowerShell（普通权限即可）** 中执行，逐条保存输出：

```powershell
# 1. 系统与硬件
Get-CimInstance Win32_OperatingSystem | Select-Object Caption, Version, BuildNumber
Get-CimInstance Win32_ComputerSystem  | Select-Object Manufacturer, Model, TotalPhysicalMemory

# 2. 网卡与无线驱动能力
Get-NetAdapter -Physical | Select-Object Name, InterfaceDescription, Status, LinkSpeed
netsh wlan show drivers
netsh wlan show wirelesscapabilities
netsh wlan show interfaces

# 3. 蓝牙设备状态
Get-PnpDevice -Class Bluetooth | Select-Object FriendlyName, Status
```

### 5.1 怎么看输出（预期与误判）

| 字段 | 预期 | 说明 |
| --- | --- | --- |
| `netsh wlan show wirelesscapabilities` 中的 **Wi-Fi Direct device** | `Supported` 才继续 | 这是 Legacy AP 路线的**必要**条件，不是充分条件 |
| 同一输出中的 **Hosted network supported** | 很可能是 `No` | **这是正常的**：现代 WDI 驱动已弃用该 API，与 Wi-Fi Direct Legacy AP 是两套东西。看到 `No` 不代表不支持 |
| `netsh wlan show drivers` 中的 `Radio types supported` | 记录实际频段 | 只用于记录环境，不用于判断可用性 |
| `Get-NetAdapter` 的 `Status = Up` | — | **不能**作为 AP 可用证据 |

采集完成后请把原始输出整段发回，并附上 `Get-Date -Format o` 的时间戳。

## 6. Legacy AP 验证说明（需两机实操，本轮不执行）

### 6.1 前置条件

1. 第 5 节的输出显示 `Wi-Fi Direct device: Supported`；
2. Windows 端能编译并运行微软官方样例 `WiFiDirectLegacy`（需要 Visual Studio 或等价工具链——**这是一项独立的环境变更，需要单独决定**）；
3. 两端在同一房间、约 1 m、无遮挡。

### 6.2 步骤（人工，可回退）

| # | 操作 | 预期输出 | 失败时 |
| --- | --- | --- | --- |
| 0 | **先确认外部网络条件**：宿主是否有上游连接、是否有其他网络接口在用 | 环境记录完整 | 只要宿主仍有上游连接（无论用哪种方式共享），该次记录就不能计入「无基础设施」条件 |
| 1 | 运行样例，设置固定 SSID 与 ≥8 位口令 | 状态显示 `Advertisement started` | 记录错误码；检查口令长度 |
| 2 | 在 Mac 上扫描 Wi-Fi 列表 | 能看到该 SSID | 检查是否为 5GHz/2.4GHz 差异；记录信道 |
| 3 | Mac 加入该网络 | 关联成功并拿到地址 | **记录实际分配到的地址**：不保证是 `192.168.137.x`，取决于 AP 实现与 DHCP 配置 |
| 4 | **先确认接收端在哪一端启动**，再测连通性 | 至少 TCP 可达 | 接收端必须在被连接的那一端先监听；未启动监听时测出的「不通」不说明路径问题 |
| 5 | 在 Mac 上 `ping <宿主地址>` 与 `nc -z <宿主地址> <端口>` | 至少 TCP 可达 | 分别记录 ICMP 与 TCP 结果（**不要用 ping 代替 TCP**）；端口取接收端实际监听值 |
| 6 | 反向：Windows 连 Mac 的监听端口（Mac 需先启动接收端） | 记录通/不通 | 若不通，记录是否为超时（而非拒绝） |
| 6 | 发送 1 MiB 文件并核对 SHA-256 | 接收端校验通过 | 记录失败阶段 |
| 7 | 停止 advertisement | 热点消失 | — |

### 6.3 恢复办法

- **停止 advertisement** 即恢复；样例进程退出会带走 AP（Wi-Fi Direct 的 AP 生命周期绑定在 publisher 对象上）。
- 若 Mac 卡在「正在加入」，在 Wi-Fi 菜单里选择其他网络或关闭再打开 Wi-Fi。
- 若 Windows 侧网络异常：优先用「设置 → 网络」界面恢复，**不要**用脚本修改适配器状态。
- 任何一步出现系统级异常，先停止实验、记录时间与现象，不要连续重试。

### 6.4 记录什么

每条记录至少包含：时间、角色（谁开 AP）、SSID 是否可见、关联结果、地址、TCP 结果、传输结果、失败阶段、人工操作数。

## 8. 与论文的关系

若 G1a 通过：可以写「我们在这对设备上建立了离线链路」，但结论仅限这对设备。
若 G1a 不通过：按主计划第 10 节，**暂停依赖该能力的实现**（B1/M 的自动会合），保留已获得的证据，重新评估范围与选题。

单次、单设备的失败**不自动构成**一篇可发表的测量论文——它只是一条证据；是否值得成文要看它能否解释出可推广的机制，这需要单独判断。

**不要把「API 调通」或「修正基础实现错误」写成研究贡献**——两者只能进实现经验。
