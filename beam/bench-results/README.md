# 基准测试数据

`beam bench` 采集的原始数据，按链路条件分文件。用 `python3 scripts/bench-summary.py` 汇总成表。

## 文件命名

| 文件 | 含义 |
| --- | --- |
| `loopback.csv` | **基线**：同一台机器自连，不含任何真实网络链路 |
| `cable.csv` | 网线直连（169.254 链路本地 / 千兆） |
| `wifi5g.csv` | 同一 WiFi，5GHz |
| `wifi24g.csv` | 同一 WiFi，2.4GHz |
| `hotspot.csv` | 一台开热点，另一台连 |
| `campus.csv` | 跨子网（Mac 有线 `10.202.4.x` → Windows WiFi `10.233.x.x`，校园网路由） |
| `relay.csv` | 经公网中转 |

## 实测一：跨子网直连（2026-11-02，校园网）

```
| 链路 | 数据量 | 次数 | 成功 | 吞吐 P50 | 建链 P50 |
| campus | 10 MB   | 3 | 3/3 | 7.1 MB/s  | 5 ms |
| campus | 100 MB  | 3 | 3/3 | 7.2 MB/s  | 4 ms |
| campus | 1000 MB | 1 | 1/1 | 6.9 MB/s  | 2 ms |
```

拓扑：Mac 有线 `10.202.4.30/24` → Windows WiFi `10.233.156.140/16`，两段之间由校园网三层路由连通；ICMP 被挡，但 TCP 9001 可通。

**结论**：

1. **稳定在 ~60 Mbps（7 MB/s）**，三次 100 MB 的方差极小（7.1–7.9），说明瓶颈是恒定带宽限制，不是抖动。
2. **1 GB 长传 144 秒，吞吐只从 7.2 掉到 6.9 MB/s（-4%）**，没有累积漂移、没有热衰减、缓冲水位稳定——数据面实现是可靠的。
3. **60 Mbps 远低于同网段 WiFi 的 30–70 MB/s**。差值来自两处：Windows 侧走 WiFi（可能是 2.4GHz 或信号一般），以及校园网跨段路由的限速。这也说明**「跨子网」本身有带宽代价**，不只是发现不到。

## 实测二：热点客户端 → 热点宿主（2026-11-02）

```
| 链路 | 数据量 | 次数 | 成功 | 吞吐 P50 | 波动范围 |
| hotspot | 10 MB  | 3 | 3/3 | 4.2 MB/s | 3.7 – 4.7 |
| hotspot | 100 MB | 3 | 3/3 | 3.6 MB/s | 2.5 – 4.8 |
```

拓扑：Mac 作为热点客户端（`192.168.137.63`），目标是热点宿主 Windows 的校园 Wi-Fi 地址 `10.233.156.140`。

**注意边界**：这是两台不同机器之间的跨设备传输，不是「同机回环」。包是否经 ICS/NAT 转发、还是宿主本地交付，本轮没有证据可判定。

**观察到的**：

1. 该组中位吞吐约为跨子网组的**一半**（3.6 vs 7.2 MiB/s），波动范围更大（2.5–4.8 vs 7.1–7.9）。
2. 每组各 3 次、单日、单设备对——**不足以断言「热点一定比跨子网慢」**，只能说在这一组条件下观察到该差异。

**不能据此推断的**：

- 不能归因到具体组件（2.4GHz / 半双工 / ICS 转发 / 宿主回环），这些都没有单独测量；
- 不能外推为「所有软 AP 都慢」；
- 不能把回环组的高吞吐当成「软件开销可忽略」的量化依据——回环与实链路的差异只能说明「瓶颈不在软件」，不能拆分各组件占比。

## 基线结果（2026-11-02，Apple Silicon / APFS SSD）

```
| 链路 | 数据量 | 次数 | 成功 | 吞吐 P50 | 吞吐 P95 | 发现 P50 | 建链 P50 |
| loopback | 10 MB   | 5 | 5/5 | 857.3 MB/s | 885.4 MB/s | 0 ms | 0 ms |
| loopback | 100 MB  | 5 | 5/5 | 721.6 MB/s | 865.7 MB/s | 0 ms | 0 ms |
| loopback | 1000 MB | 5 | 5/5 | 696.2 MB/s | 799.1 MB/s | 0 ms | 0 ms |
```

**怎么读这组数**：

1. **700–860 MB/s 是软件栈的上限**（读盘 + AES-GCM + 两端 SHA-256 + 写盘）。千兆网线 110 MB/s、WiFi 30–70 MB/s，都远低于它——说明真实链路的瓶颈在链路本身，不在实现。这是判断「值不值得优化软件」的天花板。
2. **小文件吞吐更高是缓存效应**，不是真的更快。10 MB 时发送端读取与接收端写入几乎全部命中页缓存。所以**跨规模比较吞吐没有意义，只在同一规模下比较不同链路**。
3. **P50 与 P95 差 1.2–1.5 倍**，说明本机噪声就已经不小。真实链路（尤其 WiFi）的方差会更大，所以每个条件至少 5 次、报 P50/P95，不要报平均值。

## 加一组新条件

```bash
# 接收端（另一台机器上，常驻，不要 --once）
beam recv --listen :9001 --out ~/Downloads --yes

# 发送端：一条命令跑完 10/100/1000 MB × 5 次
NOTE="5GHz ch44 rssi-52 同一房间 1m" ./scripts/bench-matrix.sh wifi5g --peer DESKTOP-4F2K
```

跑完执行：

```bash
python3 scripts/bench-summary.py
```

## 必须随数据一起记录的环境元数据

写进 `--note`（会进 CSV），否则事后无法解释差异：

- 频段与信道、RSSI（macOS：按住 Option 点 Wi-Fi 图标；Windows：`netsh wlan show interfaces`）
- 两台设备的距离与是否有遮挡
- 是否插电（省电策略会影响 Wi-Fi 功率）
- 后台是否有同步盘 / 更新在跑

## 注意

- 每份 CSV 都是**追加**写入。重复跑同一条件会累积，汇总时会一起统计——要重跑就先删文件。
- 失败记录（`ok=false`）也会写进 CSV，`error` 列是原始错误信息，这是分析失败模式的第一手材料，别删。
