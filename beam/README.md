# beam

Mac ⇄ Windows 快速传文件。单个二进制，无需安装运行时，支持跨网络。

```
Mac  ──┐                  ┌── Windows
       ├── relay (公网) ──┤
Win  ──┘   只转发密文      └── Mac
```

## 为什么不是简单的局域网直传

两台机器经常不在同一个网络（学校 ↔ 家里），而 NAT 与防火墙让「互相直连」不可靠。所以这里采用**中转**：双方都只主动出站连接一台公网可达的机器（VPS、家里常开的服务器都行），由它把两条连接配成一对后转发字节。好处是两端都不需要公网 IP、不需要端口映射。

同一局域网可以直接跳过中转，用 `--to` 点对点。

## 四条命令

```bash
# 1. 找一台双方都能连上的机器，跑中转（只需一次，长期挂着）
beam relay --listen :9000

# 2. Mac 上发送：房间码自动生成并打印
beam send 视频.mp4 --relay 你的服务器:9000
#   房间码：7K4M-QP2X

# 3. Windows 上接收
beam recv --relay 你的服务器:9000 --room 7K4M-QP2X --out D:\下载

# 4. 或者用网页界面（Windows 端不必开终端）
beam ui --relay 你的服务器:9000 --room 我收文件的房间 --out D:\下载
#   浏览器打开 http://127.0.0.1:8080
```

同一局域网：

```bash
beam recv --listen :9001                 # 接收方
beam send 文件.zip --to 192.168.1.8:9001  # 发送方
```

## 离线直连（无路由器、无互联网）

先明确一点：**完全没有物理链路就传不了数据**。能省掉的是路由器与互联网，不是链路本身。

可行的三条：

| 方式 | 说明 | 速度量级 |
| --- | --- | --- |
| **网线直连**（推荐） | USB-C 转以太网 + 普通网线，或两端都有网口。不需要路由器，两端会自动拿到 `169.254.x.x` 链路本地地址 | 千兆 ~110 MB/s |
| WiFi 热点 | Mac「系统设置 → 通用 → 共享 → 互联网共享」建热点，Windows 连上 | 数十 MB/s |
| U 盘 | 不算传输工具，但确实离线 | 取决于盘 |

**Thunderbolt 直连不推荐**：Apple 的雷雳网络只保证 Mac↔Mac，Mac↔Windows 没有可靠的驱动支持。

网线直连时最难的是「不知道对方 IP」。所以有自动发现：

```bash
# 接收方（Windows 上就是 beam.exe）
beam recv --listen :9001 --out D:\下载

# 发送方：广播查找，再按名字发
beam peers
#   发现 1 台设备：
#     DESKTOP-4F2K      169.254.31.7:9001
#   本机地址：
#     169.254.88.12/16 en7  ← 网线直连的链路本地地址

beam send 视频.mp4 --peer DESKTOP-4F2K
```

Windows 端不想开终端也可以只用网页：

```bash
beam.exe ui --tcp-listen :9001 --out D:\下载
# 浏览器打开 http://127.0.0.1:8080
# 「附近设备」下拉里选对方即可发送，收到请求同样在网页上点接收
```

### 两条发现通道

发现同时走两条路，任意一条通就够：

| 通道 | 端口 | 特点 |
| --- | --- | --- |
| UDP 广播查询/应答 | 9100 | 最简单；部分 WiFi 会过滤广播 |
| mDNS（Bonjour，`_beam._tcp`） | 5353 | 过滤策略不同；AirDrop / LocalSend 用的就是这一层 |

`beam peers` 会标出每台设备是靠哪条通道找到的（`广播` / `mDNS` / `广播+mDNS`）。

**地址不是猜的，是逐个试的**。一台机器通常有多个地址（以太网、WiFi、VPN 隧道、回环），发现阶段无法判断哪条对端可达，所以把所有候选地址都收下来，拨号时按「IPv4 链路本地 → IPv4 私网 → 其他 IPv4 → IPv6 → 回环」的顺序依次尝试，12 秒总预算。

这一条是实测踩出来的：本机同时有 `en7`（10.202.4.30）和 `utun6`（100.104.203.96，VPN 隧道），早期版本取了「第一个非回环」地址，结果连的是隧道地址，对端根本不可达。

### 四个容易踩的点

1. **Windows 防火墙**：首次运行会弹窗，必须允许「专用网络」访问，否则入站 TCP 与 UDP 都被挡。选错了可以到「Windows 安全中心 → 防火墙 → 允许应用通过」里补。
2. **链路本地地址要等**：macOS 的以太网口设为「使用 DHCP」时，拿不到服务器后要等几十秒才回落到 `169.254.x.x`。急用可以在「网络 → 以太网 → 详细信息 → TCP/IP」里手动填 `169.254.1.1` / 掩码 `255.255.0.0`，另一端填 `169.254.1.2`。
3. **广播可能被挡**：自动发现依赖 UDP 广播（端口 9100）。如果 `beam peers` 空列表但你能确认对方在听，就直接用 `--to 169.254.x.x:9001` 手动指定地址，传输本身不依赖发现。
4. **一台机器只能跑一个实例**：发现端口 9100 是独占的，第二个实例会提示「自动发现不可用」。同时开 `recv` 和 `ui` 就会撞上，改用一个，或给对方用 `--to` 地址。

## 目录与多文件

```bash
beam send 照片/                     # 整目录递归发送
beam send 照片/ 文档.pdf 说明.txt    # 目录与文件混着发
```

接收端按相对路径还原结构，并自动创建父目录：

```
照片/2026/春节.jpg
照片/封面.png
文档.pdf
```

安全约束：接收端拒绝绝对路径与任何形式的 `..`（`safeRelPath`），所以对端无法把文件写到保存目录之外的任何位置。发送端会跳过 `.beam-part` 残留文件，避免把上次中断的半截数据再传一遍。

## 链路协商

`beam send` 不再要求「三选一」。可以直接把多种目标一起给它，系统按成本从低到高依次尝试，第一个「连上且握手成功」的胜出：

```bash
beam send 文件.zip --peer DESKTOP-4F2K --to 192.168.1.8:9001 --relay host:9000 --room AB12
```

| 链路类型 | 成本 | 说明 |
| --- | --- | --- |
| `discovered` | 10 | 自动发现到的同网段地址，可能有多个 |
| `direct` | 20 | 手工指定的地址 |
| `relay` | 90 | 经中转，多一跳 |

每次尝试都会打印耗时与失败原因：

```
候选链路 5 条，按成本依次尝试：
  ✗ discovered 192.168.137.63:9082    0 ms  connect: connection refused
  ✗ discovered 172.30.244.14:9082     0 ms  connect: connection refused
  ✓ discovered 127.0.0.1:9082         0 ms
```

加 `--trace out.json` 可以把完整协商记录写成 JSON（每次尝试的类型、耗时、错误），用于分析「哪条链路先成功」「失败原因分布」。

### 能力交换（`--caps`）

```bash
beam send 文件.zip --to 192.168.1.8:9001 --caps
```

传输前先做一次 hello：双方各自声明「我是谁、在哪个端口监听、有哪些地址、支持哪些链路」，然后**对端声明的地址会被真实拨号验证**，而不是本地猜：

```
对端能力：discovered/direct（3 个地址，端口 9001）
  ✓ 可达 192.168.1.8:9001
```

设计上做了两件事：

1. **向前兼容**：能力声明挂在现有的 `Plan` 消息里（JSON 未知字段会被旧端忽略），空清单的 Plan 表示「这次是 hello，不是传输」。没有新增帧类型，也没有版本握手。
2. **不改默认行为**：不加 `--caps` 时流程与之前完全一致。启用时要求两端都是新版本——旧版接收端会把握手当成空传输拒绝。

### 链路升级：先中转见面，再改走直连

中转模式下给接收端加上 `--listen`，它就会**同时**保持直连监听：

```bash
# 接收端：经中转见面，同时监听 9002 供对端升级
beam recv --relay host:9000 --room TEST1 --listen :9002 --out ~/Downloads

# 发送端：先经中转连上，拿到对端声明的地址后自动升级
beam send 文件.zip --relay host:9000 --room TEST1 --caps
```

发送端输出：

```
  ✓ relay       host:9000/TEST1          121 ms
对端能力：discovered/direct（1 个地址，端口 9002）
  ✓ 可达 192.168.1.8:9002
已升级到直连 192.168.1.8:9002，关闭中转连接
```

**升级是单向的**：只有发起方能主动连对端。若对端在 NAT 后，它声明的地址不可达，此时安静地保留中转连接——能升级就升级，升不了不降级。

### 探测为什么需要接收端并发

能力探测会在主连接之外再开一条连接，走完「握手 + hello」才算可达。这就要求接收端**同时处理多个连接**：早期版本串行 `handle(conn)`，第二条连接只能排在 accept 队列里等，探测方拿不到握手响应。

实测后果很严重：探测的握手没有截止时间，发送端会**永久阻塞**，最后被外部杀掉。修法有两处——

- 接收端改成每个连接一个 goroutine；
- 探测连接设 2 秒截止时间，失败就判为不可达，绝不拖住主流程。

顺带补了一个区分：`Receive` 现在返回「是否真的传了文件」，探测走完 hello 不会在接收端打印「传输完成」。

### 两个来自实测的设计决定

1. **握手算协商的一部分。** 只有 TCP 连上还不够——实测遇到过隧道/VPN 代理了未监听端口，TCP 握手成功但随即被关闭（`EOF`），如果握手在协商之外，这个假连接会让整个传输失败，而后面明明还有可用候选。
2. **候选只保留 IPv4。** mDNS 会带回大量 `fe80::`（链路本地，缺 scope id 必然失败）与隧道地址（`fd7a::`、`fd00::`）。一次实测出现 13 条候选、12 条不可能通，白等 4 秒。**不可用的候选是负资产。**

## 安全模型

- **端到端加密**：两端各生成一次性 X25519 密钥，ECDH 协商后用 HKDF-SHA256 派生出双向各一把 AES-256-GCM 密钥。中转只看到密文与长度，改任何一个字节都会导致解密失败。
- **验证码**：连上后两端各显示一个 8 位码（如 `9U63-MMRE`），由会话密钥派生。两边一致说明中间没有第三方；不一致就是被中间人了。
- **房间码是唯一的入场凭证**。拿到房间码的人可以抢占这次会话——所以房间码要像密码一样对待，用完即弃（每次发送都会重新生成）。
- 中转能看到的是：谁在什么时候连了哪个房间、传输了多少字节。看不到文件名与内容。
- 没有做 PAKE，因此**首次连接时如果中转本身是恶意的**，它可以同时冒充两端（此时两端验证码会不同，需要人眼核对）。

## 传输行为

- 支持一次发多个文件，接收端整批接受或拒绝。
- 边传边算 SHA-256，接收端写完比对，不一致则删除临时文件（`.beam-part`）并报错。
- 文件名取 basename，防路径穿越；落盘后恢复原修改时间。
- 进度按字节统计，显示瞬时速率。

## 实测（2026-11，本机回环）

| 场景 | 结果 |
| --- | --- |
| 直连 64 MB | 0.08 s，SHA-256 一致，两端验证码相同 |
| 经 relay 64 MB | 0.08 s，SHA-256 一致 |
| 多文件（2.9 MB + 1.1 MB） | 两个文件哈希均一致 |
| 拒绝接收 | 发送端收到「已拒绝」，接收端不落盘 |
| 网页接受 | 清单与验证码正确，接受后完成，哈希一致 |
| 网页按路径发送 | 接收端完成，哈希一致 |
| 自动发现 + 按名字发送 | `beam peers` 发现本机（广播+mDNS，15 个候选地址），`--peer` 发送后哈希一致 |
| 多地址拨号 | 候选里同时含隧道地址 `100.104.203.96` 与局域网 `10.202.4.30`，自动选中后者 |

> 回环速度不代表真实网络。跨网络的瓶颈是两端上行带宽与中转带宽，通常 1–10 MB/s。

## 构建

```bash
./build.sh     # 产出 dist/ 下四个二进制：macOS arm64/amd64、Windows amd64/arm64
```

除 mDNS 用到 `github.com/grandcat/zeroconf`（纯 Go）外没有第三方依赖，也不需要 cgo，所以交叉编译不需要目标平台工具链。单个二进制 6.3–6.9 MB。

> `go.mod` 要求 Go 1.26：zeroconf 引入的旧版 `golang.org/x/net` 与 Go 1.26 不兼容（`syscall.recvmsg` 已被移除），已显式升级到最新版。

### 基准测试

`beam bench` 把一次传输拆成「发现 / 建链 / 传输」三段分别计时，结果追加到 CSV，用来比较不同链路的表现。接收端用普通的 `beam recv`（**不要加 `--once`**，它要连续接受多次）：

```bash
# 接收端（一直挂着）
beam recv --listen :9001 --out ~/下载 --yes

# 发送端：每种链路跑一遍，用 --label 打标签
beam bench --peer DESKTOP-4F2K --size 200 --runs 5 --label wifi5g
beam bench --to 192.168.1.8:9001 --size 200 --runs 5 --label cable
beam bench --relay host:9000 --room AB12 --size 50 --runs 5 --label relay
```

输出：

```
  #1  发现    102 ms  建链      1 ms  传输     193 ms  合计     297 ms   517.5 MB/s ( 4140 Mbps)  10.202.4.30:59359 → 10.202.4.30:9050

汇总：
  成功 5 / 5，失败 0
  发现延迟  P50    102 ms   P95    102 ms
  建链耗时  P50      1 ms   P95      1 ms
  吞吐      P50  517.5 MB/s P95  517.5 MB/s
```

一次跑完整矩阵（10/100/1000 MB × 5 次）：

```bash
NOTE="5GHz ch44 rssi-52 同一房间" ./scripts/bench-matrix.sh wifi5g --peer DESKTOP-4F2K
python3 scripts/bench-summary.py        # 汇总成 markdown 表
```

基线数据与解读见 `bench-results/README.md`。

CSV 是 **schema v2**（历史文件为 v1，脚本仍可读取，原文件不改写）：

```
schema_version, experiment_id, condition_id, trial_id, device_id, timestamp,
label, note, mode, upgrade, payload_bytes, size_mib, target, local_addr, remote_addr,
discovery_status, discovery_ms, tcp_ms, handshake_ms, negotiate_ms, transfer_ms, total_ms,
deadline_ms, failure_stage, ok, error, peer_caps_count, peer_port, final_link,
upgraded, throughput_mib_s, throughput_mbit_s, software_sha256
```

四条度量约定：

- **`payload_bytes` 是唯一的数据量基准**，`throughput_mib_s` / `throughput_mbit_s` 由它推导（1 MiB/s = 8.388608 Mbit/s）；
- **未执行的阶段写空、`discovery_status=not_run`**，不写 0——0 会被下游当成「很快」；
- **所有阶段共用一个单调时钟**，不做跨机墙钟相减；
- **每个试次结束立即落盘**，进程被杀也不丢已完成记录。

`--to` 直连模式不做发现，`discovery_status` 记 `not_run`；只有 `--peer` 才测量发现延迟。

`--caps` 会让 bench 走与 `beam send --caps` 完全相同的路径（含能力交换与升级尝试），因此 `negotiate_ms` / `peer_caps_count` / `upgraded` 才有值。

**样本量怎么读**：汇总会直接列出每个条件的成功/总数，不设「多少条才算够」的机械门槛。判断标准是看结论要多细——描述某一次运行只需要 1 次；想比较两条链路的差异，需要看配对差值的分布是否稳定，而不是数到一个固定次数就下结论。

`local_addr` 会显示实际走了哪块网卡——多网卡（VPN、有线、无线并存）时这是判断链路的关键。

两点须知：

- **发现延迟的分辨率是 100 ms**。实现上用 100 ms 小窗口轮询，而不是一次等满超时——后者会让「发现延迟」恒等于窗口长度，跨链路比较就没有意义了。
- **测试文件会缓存复用**（`/tmp/beam-bench-<size>mb.bin`），第二次起不再重新生成，避免把「生成文件」的时间算进传输。

## 为什么没有做蓝牙和「隔空投送」

这两件事卡在不同的地方，值得写清楚，免得以后重复讨论。

### 蓝牙：能做，但慢三个数量级

- 文件传输走 Bluetooth Classic 的 OBEX Object Push，理论带宽 BR/EDR 2.1 Mbps，实测吞吐通常 **100–300 KB/s**。
- 1 GB 文件约 1–3 小时；一分钟的视频也要几分钟。BLE 更慢，只适合传文本。
- 本机实测（macOS 26）：系统蓝牙栈广播的服务是 `HFP AVRCP A2DP HID LEA AACP GATT SerialPort`，**不含 OBEX OPP**；「蓝牙文件交换」工具也已被移除。也就是说 macOS 侧要自己实现 OBEX over RFCOMM 才有得用。
- 结论：传几张照片用系统「蓝牙共享」更省事；beam 不做蓝牙，因为它和「快速」这个前提冲突。

### 隔空投送：协议层跨不了系统

- AirDrop 的传输层是 **AWDL**（Apple Wireless Direct Link），跑在 802.11 的厂商自定义帧上；本机 `ifconfig awdl0` 能看到这个接口（平时 `inactive`）。
- 它是 Apple 私有实现，Windows 没有 AWDL 协议栈；开源界只有 OpenDrop 做到 macOS↔Linux，且依赖打过补丁的无线驱动。
- 所以「原生 AirDrop 跨 Mac/Windows」在协议层面不存在，不是本项目没做。

### 但「隔空投送的手感」可以跨系统

真正缺的从来不是协议，而是交互：不输 IP、不建房间、拖一下就发、对方点一下收。beam 现在具备：

- 同一广播域自动发现（`beam peers` / 网页「附近设备」下拉）；
- 端到端加密 + 验证码核对；
- 网页里**拖拽文件即发**，或按路径直发（大文件不额外落盘）；
- 对方在网页上点「接收」才开始传。

如果只需要一个成熟的现成产品，**LocalSend**（MIT，覆盖 macOS/Windows/Linux/Android/iOS）已经把纯局域网这一块做透了，直接用更省事。beam 的差异价值在**跨网络中继**——不要求两端在同一网段。

## 已知限制

1. **没有断点续传**：中断要从头再来。大文件跨网络时这是最痛的短板。
2. **不支持目录**，需要先打包（`zip -r`）。
3. **单流传输**：一条 TCP，不会像某些工具那样开多流抢带宽。
4. **中转需要你自己有一台公网机器**。没有的话：同一网段用 `--peer`/`--to` 直连，完全离线也能用；跨网络又没服务器，可以用 Tailscale/ZeroTier 组网后走 `--to`。
5. 网页界面的发送用「绝对路径」而不是文件选择框——避免浏览器上传造成一次多余的落盘与带宽浪费。Windows 上右键文件「复制文件路径」即可。
6. 没有身份持久化：每次连接都是新密钥，所以没有「信任过的设备」概念。
